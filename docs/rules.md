# 共通移行ルール・作業完了判定基準

本書を判断ルールの正本とする。手順は [procedure.md](procedure.md)、記入欄は [templates](../templates/analysis.md) に置く。同じ規則を画面ごとに転記せず、本書の版を参照する。

## 1. 対象と役割

目的は既存システムのリプレースであり、機能追加・仕様改善・既存不具合修正ではない。画面表示、入力検証、権限、遷移、DB更新、外部連携、エラー時の挙動などの観測可能な仕様を保つ。

| 役割 | 責任 |
| --- | --- |
| 依頼者／仕様判断者（人間） | 対象と除外、許容する技術的調整、判断先、作業条件を定める。仕様変更・例外を判断する |
| 作業者（AIまたは人間） | 調査、タスクの事前保存・確定、実装、検証、結果と発見事項の記録を行う |
| 確認者（人間） | 根拠と差分を確認し、必要な修正・独立した検証を行い、最終判定を記録する |

人間が役割を兼ねる場合も、作業記録と確認記録を分ける。外部への公開や本番反映は移行作業から自動的に許可されたものとしない。

## 2. 移行・技術的調整・範囲外の区別

| 区分 | 判断と扱い | 例 |
| --- | --- | --- |
| 同等移行 | 根拠があり、既存仕様を再現する。確定タスク内で実施 | Javaの検索条件をC#へ移す |
| 技術的調整 | 実行基盤の違いに対応し、業務上の意味を保つ。理由・影響・検証をタスクと報告書に残す | JSPをRazor Viewへ、既存の認証情報を案件で指定されたASP.NET Coreの仕組みに対応付ける |
| 仕様変更／改善 | 表示・入力・権限・データ・業務結果などが変わる。今回の移行に混ぜず別途報告 | 入力制限の追加、検索順の変更、操作手順の短縮 |
| 既存不具合／脆弱性 | 勝手に修正しない。発見事項として非公開で報告 | 条件漏れ、不適切な権限判定、出力処理の脆弱性 |
| 判定不能 | 根拠不足や矛盾を記録し、影響する作業を保留 | Java実装と仕様書の内容が異なる |

技術的調整と名付けるだけで仕様差を許容しない。たとえばnull・空文字、日付、丸め、文字列比較、HTTP応答、セッション、HTMLエンコードの差は業務結果や安全性に影響し得る。差が消せない、または危険な挙動の再現が必要になる場合は当該箇所を保留し、人間の判断を求める。危険な実装を機械的に複製しない。

既存不具合の別途対応が必要でも、本移行の完了基準を下げない。新しい要件は別作業として管理し、依存関係のみ本移行へ記録する。移行中に新たに作り込んだ不具合は既存不具合と区別し、元タスクの受入条件を満たすために修正・再検証する。

## 3. IDと根拠の表現

IDは案件内で一意とし、一度発行したIDを別の意味で再利用しない。複数案件をまとめる場合は案件キーを接頭辞に付ける。

| 対象 | 形式 | 用途 |
| --- | --- | --- |
| 画面 | `SCR-001` | 画面一覧、フォルダー名 |
| 概要タスク | `OV-SCR-001-001` | 全体解析から詳細タスクへの親子関係 |
| 詳細タスク | `TASK-SCR-001-001` | 指示・実績・検証の共通キー |
| 共通処理 | `COM-001` | 画面間依存。画面外の処理もここで整理 |
| 共通処理のタスク | `TASK-COM-001-001` | 画面と同じ指示書／報告書を使う。所有者を一つにする |
| ソース対応 | `MAP-001` | 全体の概略対応。詳細は報告書のタスク別対応で補う |
| 検証 | `CHK-SCR-001-001` | 受入条件と検証結果の対応 |
| 発見事項 | `FND-SCR-001-001` | 不具合・改善・不明点などの別途報告 |
| 変更要求 | `CR-SCR-001-001` | 確定後の追加・取消・条件変更の履歴 |

共通処理の検証・発見・変更要求では `SCR-001` を `COM-001` に置き換える。IDを発行する前に全体解析と既存指示書・報告書を検索し、衝突を避ける。

ソース参照は `リポジトリ識別子@固定コミット:相対パス#クラス.メソッド等` を基本とする。行番号は補助であり、行番号だけを根拠にしない。Gitを使えない場合は、変更されないスナップショットの識別子とファイルハッシュ一覧を用いる。指示書・ルール・解析文書にも固定版を記録する。

JavaとC#は1対1に限定しない。分割・統合・既存C#の再利用・廃止候補・新規基盤処理を明示する。Javaに直接対応しないC#コードも「対応なし」で終わらせず、必要性・関連タスク・技術的調整の根拠を記録する。

## 4. 指示の確定と変更管理

1. 指示書の状態を「草案」として調査し、対象・根拠・タスク・受入条件・検証方法・依存・除外を埋める。
2. 依頼で委任された範囲に収まり、実行可能なタスクは、作業者が「確定」として日時・確定者・委任根拠・固定版を保存できる。常に人間の事前承認を必須にはしない。保留タスクが残る場合はその理由と解除条件も確定時に残す。
3. 業務コードを変更する前に確定版を保存する。Gitの固定コミット、または保存日時付きの変更不可スナップショットとハッシュで識別する。自分自身のコミット値を本文へ埋め込む必要はなく、報告書から確定版を特定できればよい。
4. 確定後は元の指示書を編集せず、実施状況は報告書にだけ書く。失敗した検証条件を事後的に緩めない。
5. タスク追加・取消・条件変更が必要なら、報告書に変更要求を先に記録し、判断者・理由・影響・判断日時を残す。実装詳細の選択だけなら受入条件を変えず、実績欄に判断根拠を記録する。
6. 認められた変更は `instruction-v2.md` 等の新しい確定版として保存してから実施する。旧版を残し、後継版とCRを相互参照する。意味や条件を変更するタスクには新IDを付け、旧タスクの取消／置換と後継IDを報告書に残す。変更のないタスクは同じIDを保つ。

仕様判断・権限不足・必要入力の不足で止まる場合は、影響タスクだけ保留し、独立した確定タスクを進める。報告書は追記・訂正可能だが、過去の失敗や判断を消さず訂正理由を残す。再開時は使用版・差分・直近の検証・保留理由を確認する。

## 5. 画面追加時のsample配置とコミット

新しい画面は、ベースとするsample一式を新画面の配置先へコピーして先にコミットし、その後に画面固有の変更を加える。コピーした部分と移行のために編集した部分を、履歴と差分から区別できるようにする。

ここでいうsampleは、実案件側で指定するASP.NET Core MVCの画面ひな形一式であり、本リポジトリの文書用 `templates/`・架空の記入例 `examples/` とは別物である。sampleは実装構成の起点として使い、業務仕様の根拠はJava側に求める。

1. 指示書の確定前に、sampleの固定版、コピー元→コピー先の全ファイル、含めないファイルと理由を記録する。Controller・ViewModel・Razor Viewに加え、画面固有のJavaScript・CSS等が必要か確認する。既存の共通部品は参照先を記録し、重複コピーしない。
2. 指示書の確定版を保存してから、指定した一式を新規パスへ内容を変更せずコピーする。既存ファイルを上書きしない。コピー先のファイル名・配置先は対応表で定め、クラス名・名前空間・ルート・文言・業務処理等の内容の編集は後段で行う。
3. コピー元の固定版との内容一致とステージした差分を確認し、sample配置だけのコミットを作る。画面固有の変更、既存共通処理の変更、無関係な作業を混ぜない。このコミットを作るまで画面固有の編集を始めない。
4. sample配置コミットを起点として、名称・ルート・表示・入力・業務処理・接続・テスト等を確定タスクに沿って変更し、別のコミットに保存する。コピー元のsample自体は変更しない。複数の実装コミットに分けてもよい。
5. 報告書には変更前、sample配置、実装後の固定版と、コピー元→コピー先、対象タスク、各段階の差分を記録する。レビューや統合でもsample配置と画面固有の変更を個別に比較できる履歴を残し、両者を一つのコミットへまとめない。

コピー直後にクラス名やルートの重複等でビルド・動作確認ができない場合は、理由と状態を報告書に残す。これを避けるための内容変更も次のコミットで行う。sample配置だけではタスクの業務要件や画面の完了基準を満たしたことにはならず、実装後の版で必要な検証を行う。

sampleが未指定・読めない場合は、選定・取得に依存するタスクを保留し、独立した調査は進める。既存画面の修正など一式の新規コピーが不要な場合は、理由を指示書と報告書に記録する。Gitを使えない場合も、第3節の変更不可スナップショットとハッシュを用いて配置前・配置後・実装後を分けて保存し、配置後の固定前に画面固有の編集を始めない。

## 6. 実装方針

- 案件で固定した.NET・C#・DB・ライブラリと既存C#の規約を優先する。バージョンや依存を無断更新しない。
- ControllerでHTTP入出力と処理の調整、ViewModelで画面に必要なデータ、Razor Viewで表示を扱う。業務判断やDB操作をViewに置かない。
- 既存C#の共通処理を調査して再利用する。Javaのクラス構成を機械的にコピーしない。
- 読みやすい命名、短く理解できる処理、明確なnullの扱いを重視する。責務、共有、検証上の必要性がある場合にクラスを分ける。単なる転送用の層や実益のないinterfaceを増やさない。
- LINQや非同期処理などは対象バージョンと既存方針に合わせる。短さだけを目的に難解な記述へ変えない。
- 既存の検索順、ページング、丸め、文字コード、タイムゾーン、トランザクション境界、更新競合、例外・ログの扱いを確認する。DBや接続先の変更を暗黙に含めない。
- 認証・認可、CSRF、出力エンコード、パラメーター化などは現行と移行先の仕組みを調査する。欠陥を見つけた場合は第2節に従う。安全性と同等性が両立できない箇所を独断で解決しない。

## 7. 検証と完了判定

検証には対象版、環境、コマンドまたは操作、入力データ、期待値の根拠、実測結果、証跡を残す。正常系に加え、境界値、入力不正、権限、異常系、画面間の影響を対象に応じて選ぶ。「対象外」は理由が必要。「未実施」「環境不足」は成功ではない。

| 判定 | 必須条件 |
| --- | --- |
| Phase 1完了 | Java・既存C#の全体構成と解析台帳、概略ソース対応、画面一覧、画面別概要タスク、共通依存を保存。対象全体を棚卸しし、解析範囲・除外理由・未確認箇所と影響を開示。画面選定と詳細調査を開始できる。移行可能性の全確定を意味しない |
| タスク完了 | 確定指示に対応した結果とソース根拠があり、当該受入条件と必須検証を全て満たす |
| 作業者の作業終了 | 全タスクに結果状態があり、差分・検証・発見事項・未対応事項・再開手順を報告済み。保留や失敗があっても引き継ぎ可能。画面完了とは別 |
| 画面の移行完了 | 有効な必須タスクが全て完了し、必須検証と共通依存の接続確認が成功。未解決の阻害事項がなく、人間が差分・動作を確認して確認者・日時・対象版・判定根拠を記録 |

タスクの結果状態は「未着手／実施中／完了／保留／失敗／取消」。取消は認められたCRに結び付ける。「実装済み・検証待ち」は「実施中」とする。画面判定は「未判定／未完了／完了」とし、人間確認前や必須検証未実施のまま完了にしない。

範囲外の発見事項は、影響・別途対応先・完了を阻害するかを明示する。非阻害の既存問題が残っていても、合意した移行基準を満たせば画面を完了できる。阻害事項を「範囲外」というだけで除外しない。画面完了は本番リリース承認を意味しない。
